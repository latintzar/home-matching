# OMSRIA Architecture & Implementation Plan

**Created:** 2025-01-27  
**Purpose:** Organic Multi-Space Reduction Image Altering (OMSRIA) Process for isolating single spaces in wide-angle images

---

## 📋 Overview

The OMSRIA (Organic Multi-Space Reduction Image Altering) process is designed to systematically evaluate an image and a set of target areas for removal, determining the most efficient and physically plausible sequence of edits (camera adjustments and physical changes) required to isolate a single primary space.

**Core Constraint:** Organic plausibility - edits must simulate real-world actions (closing existing elements or changing perspective), making the resulting image suitable for consistent use in before-and-after renovation workflows.

**Pipeline Position:** Runs after **R1** (Select Best Image Per Room) and before **R2a** (Describe Room Images)

**Important:** OMSRIA only processes wide-angle images selected by R1 that have **visibility mappings** (stored in `clusters.visibility_mappings`). Images without visibility mappings (showing no other spaces) skip OMSRIA processing and proceed directly to R2a.

---

## 🎯 Problem Statement

After R1 selects the most wide-angle image per room, these images often show multiple spaces:
- Kitchen visible through arches
- Terrace with pool visible through windows
- Sitting room visible through wide doorways
- Multiple rooms visible in open-plan layouts

**Important:** OMSRIA only processes wide-angle images that have visibility mappings (stored in `clusters.visibility_mappings`). These mappings indicate which other rooms/spaces are visible in each photo. If an image has no visibility mappings (empty object or null), it means no other spaces are visible, so OMSRIA processing is not needed.

For before/after carousel workflows, we need images that isolate a single primary space when possible, while maintaining organic plausibility (no "magic" edits that couldn't happen in real life).

---

## 🏗️ Architecture

### Process Flow

```
R1 Output (Selected Wide-Angle Images)
    ↓
Filter: Only images with visibility_mappings (non-empty)
    ↓
OMSRIA Process (R1.5) - Only for images showing other spaces
    ├─ Step 1: Generate Prompt for Step 2 (Gemini 2.5 Flash) [PARALLEL]
    ├─ Step 2: Generate Editing Plan (Gemini 2.5 Flash) [PARALLEL]
    ├─ Step 3: Execute Editing Plan (Gemini 2.5 Flash Image) [PARALLEL across images, sequential per image]
    │   └─ Step 3a: Validation Loop with Retry Logic
    ├─ Step 4: Dead-End Detection [PARALLEL]
    ├─ Step 5: Optimization Pass (Gemini 2.5 Flash) [PARALLEL]
    └─ Step 6: Final Classification
    ↓
Merge: OMSRIA-processed images + Images without visibility mappings (unchanged)
    ↓
R2a Input (Optimized Before-Unfurnished Images)
```

### Models Used

- **Gemini 2.5 Flash**: Analysis, planning, validation, and optimization decisions
- **Gemini 2.5 Flash Image** (also called "nano banana"): Image editing execution - uses same VertexAI method as R3

## 📊 Detailed Process Steps

### Step 1: Generate Prompt for Step 2

**Model:** Gemini 2.5 Flash  
**Input:** 
- Selected wide-angle image from R1 (furniture-free) that has visibility mappings
- Visibility mappings from `clusters.visibility_mappings` (which spaces are visible)

**Output:** Tailored prompt for Step 2 that specifies which spaces are visible

**Process:**
1. **Filter:** Only process images from R1 that have non-empty `visibility_mappings` in `clusters`
   - Skip images with `visibility_mappings = {}` or `null` (no other spaces visible)
2. Extract visible spaces from `visibility_mappings` (we already know what's visible!)
3. Use Gemini 2.5 Flash to generate a tailored prompt for Step 2 that:
   - Specifies which spaces are visible (from visibility mappings)
   - Describes their positions (left, right, back, etc.) by analyzing the image
   - Formats the prompt according to the template below

**Prompt Template (Generated by Step 1):**
```
This image has [SPACE_1] visible in it, [position], and [SPACE_2], visible [position], and [SPACE_3] available [position].

Your goal is to make the areas mentioned above to be not visible, in an organic way, by picking the smartest out of the following options:

Closing a door
Drawing curtains
Turning the camera angle
Raising or Lowering the camera angle
A combination of the above

Decide which strategy is best.

Naturally, don't close a door where there isn't already a door. The context for this work is being able to work with the images to show before-and-after renovation images, and with our current image editing technology, it is difficult to achieve consistency in elements that show up in multiple images, hence the goal to do organic edits to the images to have simpler images to work with, which only show ONE space clearly.

If this won't be possible, if one of the mentioned areas would inevitably be visible, please say NOT POSSIBLE, and say why. If only some of the areas are possible to be obscured, say that.

Please output prompts for nano banana (Gemini 2.5 Flash Image) to perform the edits, one at a time, starting with camera angle changes and then physical changes. The prompts should be clear, efficient, and explicit.
```

**Example Output:**
```
This image has KITCHEN visible in it, on the right, and TERRACE WITH POOL, visible on the left, and SITTING ROOM available in the back.

Your goal is to make the areas mentioned above to be not visible, in an organic way...
[rest of prompt]
```

**Parallelization:** ✅ **Can process multiple images in parallel** - Each prompt generation is independent

### Step 2: Generate Editing Plan

**Model:** Gemini 2.5 Flash  
**Input:** 
- Image (furniture-free) - only for images with visibility mappings
- Prompt from Step 1 (specifies which spaces are visible and their positions)

**Note:** Only processes images that have visibility mappings indicating other spaces are visible.

**Process:**
1. Analyze image architecture (doors, windows, arches, curtains)
2. Use Step 1's prompt to understand which spaces need to be hidden
3. Determine feasibility of hiding each target area
4. Generate sequential editing plan prioritizing camera changes
5. Mark spaces as `NOT_POSSIBLE` if they can't be hidden organically
6. Mark spaces as `PARTIALLY_POSSIBLE` if only some can be hidden

**Parallelization:** ✅ **Can process multiple images in parallel** - Each editing plan generation is independent

### Step 3: Execute Editing Plan

**Model:** Gemini 2.5 Flash Image (same method as R3 uses)  
**Input:** Editing plan from Step 2 (only for images with visibility mappings)  
**Output:** Edited image(s) with spaces hidden

**Process:**
1. Execute each step in the editing plan sequentially (per image)
2. For each step:
   - Call Gemini 2.5 Flash Image using VertexAI (same method as R3)
   - Use the result as input for the next step
   - After each step, validate that the target area is fully obscured

**Parallelization:** 
- ⚠️ **Sequential per image** - Steps within an image must run sequentially (each depends on previous)
- ✅ **Parallel across images** - Multiple images can be processed in parallel (each image's editing plan is independent)

**Implementation (Same as R3):**

#### Step 3a: Validation Loop with Retry Logic

**Critical Feature:** After each Gemini 2.5 Flash Image edit, validate that the target space is fully obscured.

**Process:**
1. **After each edit**, use Gemini 2.5 Flash to check if target space is fully obscured
2. **If not fully obscured:**
   - Rerun the same Gemini 2.5 Flash Image prompt (no changes)
   - Track retry count (max 10 retries)
   - Repeat until fully obscured or max retries reached
3. **If fully obscured:** Proceed to next step
4. **If max retries reached:** Mark as `PARTIALLY_POSSIBLE` or `NOT_POSSIBLE` and move on

**Why This Works:**
- Gemini 2.5 Flash Image sometimes needs multiple attempts with the same prompt
- Retrying with identical prompt eventually achieves full obscuration (typically within 10 attempts)
- No prompt modification needed - just persistence

**Validation Prompt:**
```
Analyze this image and determine if the target space "[TARGET_AREA]" is FULLY OBSCURED.

TARGET AREA: [e.g., "KITCHEN"]
IMAGE: [Current edited image]

Check:
1. Is ANY portion of the target area visible?
2. Can you see through to the target space?
3. Is the target area completely hidden from view?

Return JSON:
{
  "is_fully_obscured": true | false,
  "reasoning": "Explanation",
  "visible_portions": ["Description of any visible parts"] // empty if fully obscured
}
```

**Implementation:**
```typescript
import { VertexAI } from '@google-cloud/vertexai';

const vertexAI = new VertexAI({
  project: process.env.GOOGLE_CLOUD_PROJECT_ID!,
  location: process.env.GOOGLE_CLOUD_LOCATION || 'us-central1',
});

const model = vertexAI.getGenerativeModel({
  model: 'gemini-2.5-flash-image',
  generationConfig: {
    temperature: 0,
    topP: 0.7,
    maxOutputTokens: 32768,
    responseModalities: ['IMAGE']
  } as any,
  safetySettings: [
    { category: 'HARM_CATEGORY_HATE_SPEECH', threshold: 'OFF' },
    { category: 'HARM_CATEGORY_DANGEROUS_CONTENT', threshold: 'OFF' },
    { category: 'HARM_CATEGORY_SEXUALLY_EXPLICIT', threshold: 'OFF' },
    { category: 'HARM_CATEGORY_HARASSMENT', threshold: 'OFF' }
  ] as any
});

async function executeEditingStep(
  step: EditingStep,
  currentImageBase64: string,
  currentImageContentType: string,
  maxRetries: number = 10
): Promise<{ success: boolean; image: string; retries: number }> {
  let imageBase64 = currentImageBase64;
  let retries = 0;
  
  while (retries < maxRetries) {
    // Execute Gemini 2.5 Flash Image edit (same method as R3)
    const parts = [
      { text: step.prompt },
      {
        inlineData: {
          mimeType: currentImageContentType,
          data: imageBase64
        }
      }
    ];

    const result = await model.generateContent({
      contents: [{
        role: 'user',
        parts: parts
      }]
    });

    // Extract image from response (same pattern as R3)
    const imagePart = result.response.candidates[0]?.content?.parts?.find(
      (p: any) => p.inlineData?.data
    );
    
    if (!imagePart?.inlineData?.data) {
      throw new Error('No image generated');
    }
    
    const editedImageBase64 = imagePart.inlineData.data;
    
    // Validate obscuration
    const validation = await validateObscuration(editedImageBase64, step.target_area_hidden);
    
    if (validation.is_fully_obscured) {
      return { success: true, image: editedImageBase64, retries };
    }
    
    // Not fully obscured - retry with same prompt
    imageBase64 = editedImageBase64; // Use current result as base for next attempt
    retries++;
  }
  
  return { success: false, image: imageBase64, retries };
}
```

### Step 4: Dead-End Detection

**Process:**
1. After executing editing plan, check Decision field:
   - `POSSIBLE`: Successfully isolated single space → Mark as `SINGLE_SPACE`
   - `PARTIALLY_POSSIBLE`: Some spaces hidden, others unavoidable → Mark as `DEAD_END`
   - `NOT_POSSIBLE`: Cannot hide target spaces organically → Mark as `DEAD_END`

2. Store results with metadata:
   - `image_type`: `SINGLE_SPACE` | `DEAD_END`
   - `visible_spaces`: List of spaces still visible
   - `hidden_spaces`: List of spaces successfully hidden
   - `unavoidable_spaces`: List of spaces that couldn't be hidden

**Storage:**
- New table: `omsria_processed_images`
- Columns:
  - `listing_id`
  - `room_id` (primary space)
  - `image_url` (before-unfurnished URL)
  - `image_type` (`SINGLE_SPACE` | `DEAD_END`)
  - `visible_spaces` (JSONB array)
  - `hidden_spaces` (JSONB array)
  - `unavoidable_spaces` (JSONB array)
  - `editing_plan` (JSONB - full OMSRIA output)
  - `retry_counts` (JSONB - retry counts per step)
  - `created_at`

### Step 5: Optimization Pass

**Model:** Gemini 2.5 Flash  
**Goal:** Eliminate redundant single-space images when they're already shown in multi-space DEAD_END images

**Input:** All processed images from Step 4 (only images that had visibility mappings and were processed)

**Note:** We already know which spaces are visible/unavoidable from Step 2's output (`Areas_Hidden`, `Areas_Unavoidable`). No need to re-identify spaces.

**Process:**

#### 5.1: Extract Space Information from Step 2 Output

For each processed image, extract visible spaces from Step 2's OMSRIA output:

**Input:** All processed images (SINGLE_SPACE + DEAD_END) with their Step 2 editing plans  
**Output:** Space visibility map (derived from Step 2 output, not re-analyzed)

**How:**
- For SINGLE_SPACE images: `visible_spaces = [primary_space]` (all others were hidden)
- For DEAD_END images: `visible_spaces = Areas_Hidden + Areas_Unavoidable` (from Step 2 output)

**Example:**
```json
{
  "images": [
    {
      "image_id": "img_1",
      "image_url": "https://...",
      "image_type": "SINGLE_SPACE",
      "visible_spaces": ["KITCHEN"],  // From Step 2: all others hidden
      "primary_space": "KITCHEN"
    },
    {
      "image_id": "img_2",
      "image_url": "https://...",
      "image_type": "DEAD_END",
      "visible_spaces": ["KITCHEN", "SITTING_ROOM"],  // From Step 2: Areas_Unavoidable
      "unavoidable_spaces": ["SITTING_ROOM"]  // From Step 2 output
    },
    {
      "image_id": "img_3",
      "image_url": "https://...",
      "image_type": "SINGLE_SPACE",
      "visible_spaces": ["SITTING_ROOM"],  // From Step 2: all others hidden
      "primary_space": "SITTING_ROOM"
    }
  ]
}
```

**Parallelization:** ✅ **Can process multiple images in parallel** - Simple data extraction from Step 2 output

#### 5.2: Redundancy Detection (Logic)

1. Group images by visible spaces
2. Find DEAD_END images showing multiple spaces
3. For each DEAD_END, check if all its spaces also exist as SINGLE_SPACE images
4. Identify redundancy cases

**Example:**
- DEAD_END shows: `["KITCHEN", "SITTING_ROOM"]`
- SINGLE_SPACE images exist for: `["KITCHEN"]` and `["SITTING_ROOM"]`
- **Redundancy detected:** Both single-space images are redundant

#### 5.3: Selection Decision (Gemini 2.5 Flash)

For each redundancy case, compare:
- The DEAD_END multi-space image
- The set of single-space images covering the same spaces

**Decision Criteria:**
- Clarity/quality of the multi-space view
- Whether single-space images are clearer individually
- Which set better serves the before/after workflow

**Parallelization:** ✅ **Can process multiple redundancy cases in parallel** - Each comparison is independent

**Prompt:**
```
You are comparing images to determine which to keep for a before/after renovation workflow.

DEAD_END MULTI-SPACE IMAGE:
- Shows: [list of spaces]
- Image: [image]

SINGLE-SPACE IMAGES:
- Image 1: Shows [space1] - [image]
- Image 2: Shows [space2] - [image]

TASK:
Determine which set provides better value for renovation visualization:
1. Keep the multi-space DEAD_END image and discard single-space images?
2. Keep the single-space images and discard the DEAD_END?

Consider:
- Clarity of each space in multi-space vs single-space views
- Which is more useful for before/after comparison
- Quality and composition

Return JSON:
{
  "decision": "KEEP_MULTI_SPACE" | "KEEP_SINGLE_SPACES",
  "reasoning": "Explanation",
  "images_to_keep": ["image_id_1", "image_id_2"],
  "images_to_discard": ["image_id_3"]
}
```

#### 5.4: Final Classification

1. Keep selected SINGLE_SPACE images
2. Mark selected DEAD_END images as `MULTI_SPACE`
3. Discard redundant images
4. Update `omsria_processed_images` table:
   - `image_type`: Update `DEAD_END` → `MULTI_SPACE` for kept multi-space images
   - `is_redundant`: Mark discarded images as `true`

### Step 6: Final Output

**Output:** Optimized set of before-unfurnished images

**Final Image Types:**
- `SINGLE_SPACE`: Successfully isolated single space
- `MULTI_SPACE`: Multiple spaces visible (no redundancy with single-space images)

**Handling Images Without Visibility Mappings:**
- Images without visibility mappings (no other spaces visible) skip OMSRIA processing
- These images are stored directly in `omsria_processed_images` with:
  - `image_type`: `SINGLE_SPACE` (they already show only one space)
  - `visible_spaces`: `[primary_space]` (just the room itself)
  - `hidden_spaces`: `[]` (nothing to hide)
  - `unavoidable_spaces`: `[]` (nothing unavoidable)
  - `image_url`: Furniture-free URL from F0 (no edits needed)

**Storage:**
- Images stored in: `property-images/{listing_id}/before-unfurnished/`
- Metadata in: `omsria_processed_images` table
- All images (processed and unprocessed) stored in same table for R2a

**Integration with R2a:**
- R2a reads from `omsria_processed_images` for ALL images
- OMSRIA-processed images: Use `image_url` from OMSRIA output
- Images without visibility mappings: Use furniture-free URL (stored as `image_url`)
- R2a uses these images as the "before-unfurnished" images throughout the R pipeline

## 🎯 Single-Space vs Multi-Space: Definition & Redundancy Elimination

### Core Definitions

#### SINGLE_SPACE Image
- **Definition:** An image that shows exactly ONE primary space, with all other visible spaces successfully hidden through organic edits
- **Creation:** Result of successful OMSRIA process where `Decision: POSSIBLE` and all target areas were hidden
- **Example:** Kitchen image where terrace and sitting room are completely obscured

#### MULTI_SPACE Image
- **Definition:** An image that shows MULTIPLE spaces, where at least one space could not be hidden organically
- **Creation:** Result of OMSRIA process where `Decision: PARTIALLY_POSSIBLE` or `NOT_POSSIBLE`, and some spaces are unavoidable
- **Initial State:** Marked as `DEAD_END` in Step 4
- **Final State:** Reclassified as `MULTI_SPACE` in Step 5 if kept after optimization

### Redundancy Problem

**The Problem:**
After Step 4, we might have:
- A MULTI_SPACE (DEAD_END) image showing `["KITCHEN", "SITTING_ROOM"]` (from Step 2's `Areas_Unavoidable`)
- A SINGLE_SPACE image showing `["KITCHEN"]` (all others hidden)
- A SINGLE_SPACE image showing `["SITTING_ROOM"]` (all others hidden)

This is redundant - the two single-space images together show the same spaces as the multi-space image.

### Redundancy Elimination Process

#### Step 5.1: Extract Space Information from Step 2 Output

For each processed image, extract visible spaces from Step 2's OMSRIA output:
- **SINGLE_SPACE images:** `visible_spaces = [primary_space]` (all others were successfully hidden)
- **DEAD_END images:** `visible_spaces = Areas_Hidden + Areas_Unavoidable` (from Step 2's output)

**No re-analysis needed** - Step 2 already told us which spaces are unavoidable!

#### 5.2: Detect Redundancy Cases

**Algorithm:**
```typescript
// For each DEAD_END image showing multiple spaces
for (const deadEndImage of deadEndImages) {
  const deadEndSpaces = deadEndImage.visible_spaces; // e.g., ["KITCHEN", "SITTING_ROOM"]
  
  // Find all SINGLE_SPACE images that show spaces contained in this DEAD_END
  const matchingSingleSpaces = singleSpaceImages.filter(single => 
    deadEndSpaces.includes(single.visible_spaces[0])
  );
  
  // If ALL spaces in DEAD_END have corresponding SINGLE_SPACE images, redundancy detected
  const singleSpaceSpaces = matchingSingleSpaces.map(s => s.visible_spaces[0]);
  const allSpacesCovered = deadEndSpaces.every(space => singleSpaceSpaces.includes(space));
  
  if (allSpacesCovered && matchingSingleSpaces.length === deadEndSpaces.length) {
    // Redundancy case: DEAD_END shows same spaces as collection of SINGLE_SPACE images
    redundancyCases.push({
      deadEndImage,
      singleSpaceImages: matchingSingleSpaces
    });
  }
}
```

**Example:**
- DEAD_END: `visible_spaces: ["KITCHEN", "SITTING_ROOM"]`
- SINGLE_SPACE 1: `visible_spaces: ["KITCHEN"]`
- SINGLE_SPACE 2: `visible_spaces: ["SITTING_ROOM"]`
- **Result:** Redundancy detected - DEAD_END shows same spaces as SINGLE_SPACE 1 + SINGLE_SPACE 2

#### 5.3: Decision Making (Gemini 2.5 Flash)

For each redundancy case, Gemini decides which to keep:

**Input:**
- DEAD_END multi-space image
- Set of SINGLE_SPACE images covering the same spaces

**Decision Criteria:**
1. **Clarity:** Which set shows each space more clearly?
2. **Composition:** Which set has better composition for before/after workflow?
3. **Usefulness:** Which set is more useful for renovation visualization?

**Output:**
- `KEEP_MULTI_SPACE`: Keep DEAD_END, discard SINGLE_SPACE images
- `KEEP_SINGLE_SPACES`: Keep SINGLE_SPACE images, discard DEAD_END

#### 5.4: Final Classification

**Actions:**
1. **If KEEP_MULTI_SPACE:**
   - Keep DEAD_END image
   - Mark DEAD_END as `MULTI_SPACE` (reclassify)
   - Mark SINGLE_SPACE images as `is_redundant: true`

2. **If KEEP_SINGLE_SPACES:**
   - Keep SINGLE_SPACE images
   - Mark DEAD_END as `is_redundant: true`

3. **Update database:**
   ```sql
   -- Reclassify DEAD_END to MULTI_SPACE if kept
   UPDATE omsria_processed_images 
   SET image_type = 'MULTI_SPACE' 
   WHERE id = dead_end_id AND is_redundant = false;
   
   -- Mark redundant images
   UPDATE omsria_processed_images 
   SET is_redundant = true 
   WHERE id IN (redundant_image_ids);
   ```

### Final State Guarantee

**After Step 5 Optimization, the final set guarantees:**

1. **No Redundancy:**
   - If a MULTI_SPACE image shows `["SPACE_A", "SPACE_B"]`, there are NO SINGLE_SPACE images showing `["SPACE_A"]` or `["SPACE_B"]` individually
   - If SINGLE_SPACE images exist for `["SPACE_A"]` and `["SPACE_B"]`, there is NO MULTI_SPACE image showing both

2. **Complete Coverage:**
   - Every space visible in the original images is represented in at least one final image
   - No spaces are lost in the optimization process

3. **Clear Classification:**
   - `SINGLE_SPACE`: Shows exactly one space (no redundancy)
   - `MULTI_SPACE`: Shows multiple spaces (no single-space alternatives exist for those spaces)
   - `is_redundant: true`: Discarded images (not used in pipeline)

**Step 5.2: Redundancy Detection**

```
- All spaces covered by single-space images → REDUNDANCY
```

**Step 5.3: Decision (Gemini)**
```
Decision: KEEP_MULTI_SPACE
Reasoning: "The multi-space image shows the relationship between kitchen and sitting room better, and both spaces are clearly visible."
```

**Step 5.4: Final Classification**
```
Image 1: SINGLE_SPACE → is_redundant: true (discarded)
Image 2: DEAD_END → MULTI_SPACE, is_redundant: false (kept)
Image 3: SINGLE_SPACE → is_redundant: true (discarded)
Image 4: SINGLE_SPACE → is_redundant: false (kept)
```

**Final Output:**
```
Image 2: MULTI_SPACE, visible_spaces: ["KITCHEN", "SITTING_ROOM"]
Image 4: SINGLE_SPACE, visible_spaces: ["DINING_ROOM"]
```

**Result:** No redundancy - KITCHEN and SITTING_ROOM only appear together in the MULTI_SPACE image, not individually.

## 🗄️ Database Schema

### New Table: `omsria_processed_images`

```sql
CREATE TABLE omsria_processed_images (
  id BIGSERIAL PRIMARY KEY,
  listing_id BIGINT NOT NULL REFERENCES listings(id) ON DELETE CASCADE,
  room_id TEXT NOT NULL, -- e.g., "cluster_123"
  image_url TEXT NOT NULL, -- URL to before-unfurnished image
  image_type TEXT NOT NULL CHECK (image_type IN ('SINGLE_SPACE', 'DEAD_END', 'MULTI_SPACE')),
  visible_spaces JSONB NOT NULL DEFAULT '[]'::jsonb, -- Array of space names
  hidden_spaces JSONB NOT NULL DEFAULT '[]'::jsonb, -- Array of successfully hidden spaces
  unavoidable_spaces JSONB NOT NULL DEFAULT '[]'::jsonb, -- Array of spaces that couldn't be hidden
  editing_plan JSONB, -- Full OMSRIA output from Step 2
  retry_counts JSONB, -- Retry counts per editing step: {"step_1": 3, "step_2": 1}
  is_redundant BOOLEAN NOT NULL DEFAULT false, -- True if discarded in optimization pass
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  
  UNIQUE(listing_id, room_id)
);

CREATE INDEX idx_omsria_listing ON omsria_processed_images(listing_id);
CREATE INDEX idx_omsria_room ON omsria_processed_images(room_id);
CREATE INDEX idx_omsria_type ON omsria_processed_images(image_type);
CREATE INDEX idx_omsria_redundant ON omsria_processed_images(is_redundant) WHERE is_redundant = false;
```

## 🔍 Error Handling

### Common Error Cases

1. **Gemini 2.5 Flash Image fails to obscure space after max retries**
   - Mark as `PARTIALLY_POSSIBLE` or `NOT_POSSIBLE`
   - Continue with next space

2. **Gemini analysis fails**
   - Retry with exponential backoff (max 3 retries)
   - Log error and skip image

3. **Image fetch fails**
   - Log error and skip image
   - Continue with other images

4. **Storage upload fails**
   - Retry upload (max 3 retries)
   - Log error and mark as failed

## 📊 Performance Considerations

### Parallelization Opportunities

**Step 1: Identify Visible Spaces**
- ✅ **Parallel:** Can process multiple images in parallel (batch Gemini calls)
- Each image analysis is independent

**Step 2: Generate Editing Plan**
- ✅ **Parallel:** Can process multiple images in parallel (batch Gemini calls)
- Each editing plan generation is independent

**Step 3: Execute Editing Plan**
- ⚠️ **Sequential per image:** Steps within an image must run sequentially (each depends on previous)
- ✅ **Parallel across images:** Multiple images can be processed in parallel (each image's editing plan is independent)

**Step 4: Dead-End Detection**
- ✅ **Parallel:** Can process multiple images in parallel (simple classification logic)

**Step 5: Optimization Pass**
- ✅ **Step 5.1 (Extract Space Info):** Can process multiple images in parallel (simple data extraction from Step 2 output)
- ✅ **Step 5.2 (Redundancy Detection):** Sequential logic (needs all space info extracted first)
- ✅ **Step 5.3 (Selection Decision):** Can process multiple redundancy cases in parallel
- ✅ **Step 5.4 (Final Classification):** Sequential database updates

### Recommended Parallelization Strategy

1. **Step 1 & 2:** Process all images in parallel batches (e.g., 5-10 images per batch)
2. **Step 3:** Process images in parallel, but keep steps sequential within each image
3. **Step 5:** Process space extraction and selection decisions in parallel batches

### Caching

- Cache Gemini analysis results for identical images
- Cache editing plans for similar image configurations

### Rate Limiting

- Respect Gemini API rate limits
- Implement exponential backoff for rate limit errors
